# ADR 0006：窗口微批、紧凑检查点与分析物化隔离

日期：2026-11-08。状态：实现并持续验收，最终指标以原始报告为准。

## 问题与决策

逐日请求数据库即使放在同一事务中，仍产生大量重复的网络查询。改为最多64窗口的有界处理函数，实时消费默认每组最多16窗口，不等待凑批。一次读取运行、模型、最近特征和HMM过滤向量；严格按消息顺序计算；批量写入特征、过滤状态、结果、outbox及最后消费偏移。重复窗口跳过；缺失历史或逆序拒绝。SQL失败时整个微批回滚，Kafka偏移只在业务提交后确认。单条路径调用同一函数，避免两套算法漂移。

特征投递到ClickHouse的持久outbox，每个窗口保存一个包含原事实ID的信封，物化时展开，兼容旧单事实格式。outbox发送确认由逐条UPDATE改为有界IN批更新。Kafka转发和ClickHouse物化使用不同线程，分析库写入不会阻塞已提交状态的实时推送；两者均从持久outbox重试。ClickHouse仍为最终一致，不声称与SQL跨库严格exactly-once。

Flink原有String检查点、状态名和UID保留，但滚动历史仅保存计算、排序和去重需要的值、日期、事件ID；最新完整原观测用于输出来源证据。InputGuard只保存去重所需字段，读取旧完整JSON仍兼容。减少重复JSON解析和无用元数据序列化。计算规则、20次观测窗口、收益率bps口径、模型版本及原始事件ID不变。

## 验证与代价

合成单测核对旧/紧凑历史的特征结果一致、重复判断、HMM预热、重启、陈旧输入、前向过滤及不可变上一步快照。真实完整官方回放核对861状态与离线参照，最大概率差约1.21e-13。2026-11-08首次微批/紧凑状态回放约20.8秒，端到端P95约600ms，相较旧版本有改善，但不能称100ms达标。这是早期迭代的失败基线；后续解耦、完整故障与最新数字见release/性能与测试报告.md和原始JSON。

微批会增加单条等待，故限制批大小且不主动等待。每个运行的HMM递推仍顺序执行，不能通过乱序并发破坏模型语义。增加线程不等于增加成功处理能力，物化积压单独可见。任何优化不得省略SQL持久化、Kafka确认、幂等与检查点来制造时延成绩。

## 冻结推断与服务隔离补充

实时默认使用 Flink 内的冻结 GMM/HMM/PCA 数学推断。不可变 run_config 事件包含规范模型字节与 SHA256，Java 只验证和评分，不重新拟合。保留原 Python 推断路径用于旧运行与交叉核验；同一模型黄金样本和官方完整回放验证误差。新增 operator UID，原历史 String 状态与 UID 保留。编译推断的状态先进入预警服务事务，SQL 提交后经 quantos.persisted-states.v1/outbox 再进 Redis/WS，避免缓存领先持久事实。

发布器在独立 Python 子进程运行，MySQL 单发布器租约、每500条确认与断点语义不变，CPU序列化不再竞争HTTP/WS解释器。正数输入速率按32条小段平滑配速，不以500条大突发冒充稳定输入；0明确为最大速度。输入配速和端到端时延测量分开，不据此宣称十万条每秒容量。

分段时钟发现部分尾部样本在特征完成至冻结推断之间等待约99ms，计算仅数微秒。Flink网络缓冲改为1ms；低延迟与峰值吞吐之间有代价，仍须用实际报告判断。依据：[Flink低延迟官方说明](https://flink.apache.org/2022/05/18/getting-into-low-latency-gears-with-apache-flink-part-one/)、[网络内存与缓冲官方说明](https://nightlies.apache.org/flink/flink-docs-stable/docs/deployment/memory/network_mem_tuning/)。

传输使用orjson，显式拒绝非有限数字；规范内容哈希仍调用原canonical/identity，不受JSON键顺序优化影响。参考：[orjson源项目](https://github.com/ijl/orjson)。网关保持每次请求的实时注销检查，仅调整有界Jedis连接池，队列/认证/Redis开销分别测量；不通过放弃身份检查改善成绩。
