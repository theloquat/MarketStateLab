# 核心逻辑与答辩速读

这是帮助理解真实实现的阅读路线。先能解释一次数据如何走完全程，再看组件名称。最终判断和现场回答需要参赛者自己掌握。

1. **我们识别什么？** 固定8个核心资产的20次观测动量与波动，训练出三类压力状态。名称按训练期风险方向映射。39个资产都可查，核心8个是一项版本决策，不能把三类概率解释成涨跌概率。
2. **有没有偷看未来？** 训练截止固定2022-12-31，缩放、PCA、状态命名均冻结。HMM只前向过滤，过去输入预热，不用测试期后向平滑。日期+2自然日是重建假设，不能宣称真实历史发布时间已获认证。
3. **为什么债券收益率另算？** 收益率百分数的差乘100是bps，价格用比例变化；收益率不等于债券总回报。非正价格保留原件但打断比例收益窗口。
4. **为什么需要Kafka？** 持久缓冲、解耦生产和消费、在确认偏移前失败后重放。Kafka至少一次投递仍会重复，业务层用稳定事件ID和主键去重。
5. **Flink做什么？** 输入校验/隔离与去重、UTC可得日期日窗口、20次观测滚动特征、冻结模型评分。Checkpoint保存当前滚动历史和HMM过滤向量，Savepoint用于受控升级和停机。
6. **两个时钟有什么区别？** observation_date是供应商观测日，available_date是重建可得日；watermark_date是多次历史回放隔离使用的递增逻辑时钟。Kafka记录时间和性能测量使用真实处理墙钟，防止虚拟未来日期破坏保留期。
7. **MySQL事务保护什么？** 一个窗口微批的特征/状态、过滤向量、预警、投递记录和消费偏移共同提交。失败整批回滚；Kafka偏移在SQL提交后确认。崩溃后重放不应重复形成业务事实。
8. **为什么有outbox？** SQL提交后再向Kafka/Redis/ClickHouse发送。若转发失败，持久投递记录仍在，重试可去重；缓存不能先出现未提交的结论。ClickHouse是最终一致分析副本，不是主事务库。
9. **Redis、Caffeine能否代替数据库？** 不能。Redis保存可重建的最新状态与事件广播；Caffeine仅缓存同角色均可读的官方查询结果300ms。每次HTTP仍验证JWT和即时注销；角色、写权限和来源在服务端再次检查。
10. **如何证明恢复？** 中途SIGKILL TaskManager和两消费服务，恢复后核对64652输入/特征、2406日窗口、861状态、26预警；MySQL、ClickHouse FINAL、Redis和离线参照逐项比对。源码位置：distributed.py、batching.py、MarketFeatures.java、RunInference.java。
11. **Agent能做什么？** 一次付费请求提出受schema限制的研究工具任务，先批准再运行。工具有输入、版本、结果与反证，没有任意shell/代码执行、真实订单或自动收费重试。接纳结论并不使其自动成为实盘策略。
12. **模型真的有效吗？** 当前压力画像具有描述性，但未来十次SPX收盘跌5%的任务上，复杂模型F1低于固定价格规则；文本消融也未显示增益。报告负结果是评价的一部分，不能用工程复杂度代替效果论证。
13. **性能测量从哪里到哪里？** 端到端从Flink关窗触发到客户端收到已持久化结果，不含等待1d业务窗口和水位线前接入。Redis/WS局部时延另列；完整回放条数除耗时包含预热与启动，不能当十万条每秒持续容量证明。
14. **本机分布式等于高可用吗？** 多个独立进程确实通过Kafka、数据库和网络执行，但所有组件仍在一台主机。进程故障恢复已测，整机损坏或多机容灾尚未验证。
